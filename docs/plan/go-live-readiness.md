# Go-live readiness checklist

Development is dev-only until go-live (D-263): a local Supabase, no hosted project, no real clients. Everything that decision and its companions defer is listed here. The owner ticks an item when it is decided and done. Reviewing this list is part of the Phase 5 gate (task P5-T12) and no real client is onboarded before every item is ticked or accepted as a risk in writing (D-296).

| [ ] | G20 | Database privileges | Supabase's default grants leave `TRUNCATE`, `TRIGGER` and `REFERENCES` on every table to `authenticated` and `service_role`, so `truncate approvals` works over a direct SQL connection and skips RLS and the append-only trigger; `advance_stage()` and the guard and stamp trigger functions keep the default PUBLIC execute (the function itself refuses anon). | [ ] | G24 | Atomic Accept | The Approval queue Accept runs the approval insert, the artifact update and `advance_stage` as separate calls. | [ ] | G25 | Direct run updates | The owner policy on `stage_runs` still allows any update by an owner session, so a console bug or a stolen owner session could set a run to `succeeded` without the queue functions. The service key can also write the table directly. | Allow status changes only through `enqueue_run`, `claim_run`, `finish_run` and `request_run_cancel` (a guard trigger like `guard_stage_change`), with a break check for each. | D-264, D-302 |
| [ ] | G26 | Run logs and waiting runs | The runner writes to the console only, not to `run_logs`. A `waiting` run is never re-queued by the stale rule and has no timeout, so a run that waits for an approval nobody gives holds its project's slot until the owner cancels it. | Write start, finish and error lines to `run_logs` with the run's trace id; decide a waiting timeout when the first stage that waits is built. Also: after the 10-second grace a handler that ignores the abort keeps running in the process (real handlers need a process kill); a worker whose heartbeats fail keeps working after another worker has recovered the run; a queued run whose project has left its stage stays queued forever (cancel queued runs when the stage advances); a run keeps the first attempt's `started_at`, so a retried run shows a long duration. | D-084, D-278, D-302 |
| [ ] | G27 | Intake round rules in the database | The round rules (only an open round takes answers, submit, reopen and unlock, required fields at Submit) are enforced in the console code, as the owner chose for P2-T03; the owner session can still write any `intake_rounds` or `intake_responses` row by other means. Before real clients (and certainly before client logins, G15) move them into database functions and triggers with deliberate-break checks. |
| [ ] | G28 | Upload safety | Uploaded files stay `scan_status = 'pending'`: there is no malware scan, no SVG sanitising, no check of the file's real content against its extension (the console trusts the extension, not the browser's type), and the 5 MB image cap (D-211) is enforced by the uploads table and the console, not by the bucket. The console lists the files but has no download or preview link yet. Agents must not open an upload until it is scanned (D-098). |
