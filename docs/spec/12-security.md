# Security and credentials

> Originally taken from a Claude Doc (2026-10-05) that has since been retired. The repo is the source of truth; this file reflects the owner-approved decisions recorded in `DECISIONS.md`. Agents change files in `docs/spec/` only after the owner approves a proposal in `docs/proposals/` (see `AGENTS.md`).

The main risks are agents with shell access on the owner's own machine, client data in Supabase, and credentials in the handover.

- **Worker isolation:** run each agent run in its own container (no host mounts, non-root, scrubbed environment, egress limited to the npm registry, GitHub and the Anthropic API) with a per-project working directory (D-266); only the orchestrator holds the Supabase service key and connects to the database, and agent runs hold no Supabase or database credentials (D-264, D-295); give workers only a short-lived GitHub App token limited to that project's repository. Workers hold no Vercel token. Never expose personal or account-wide tokens to workers.
- **Approval enforcement:** stage transitions happen only through a server-side function that checks for an approval record; agents cannot write to `stage` directly.
- **Row-level security:** clients see only their own project's client-facing rows; the owner role is membership in the `owners` table, checked in the database. The owner account uses email + password with no multi-factor, now or at go-live (accepted risk); a hard-gate Accept needs the project name typed (D-268). Helper functions live in a private schema and security-definer functions use an empty `search_path` (D-271).
- **Client accounts:** email + password through Supabase Auth, with password-strength rules and rate limiting; accounts stay active after close until the owner disables them manually, and a project can have several client logins, but only the project's named client signer's approval counts at client gates. Public sign-ups are off and client passwords have a minimum length of 12.
- **Secrets:** environment variables for API keys; no client secrets stored in the pipeline database, with one exception: the handover document, which may contain credentials (see below; stored in the database as an accepted risk and a go-live item, D-273). Client-owned secrets (such as the form mailbox's password) are entered directly into the client's own Vercel project when possible.
- **Handover document:** generated once as part of the handover guide and shown to the client on the dashboard; manual sharing is no longer required. It may contain credentials, which the owner accepts as a known risk. It is stored in the database (and so in backups for up to 180 days), readable by the client and the owner, and erased by the retention job at the retention date. It becomes visible to the client only after the owner's approval of the handover stage, and the database refuses to make it client-visible before that (D-251).
- **Data handling:** uploaded assets are stored in private Supabase storage and deleted, together with intake data and the handover guide's contents and PDF, 90 days after close (adjustable per project).
- **Agent safety:** treat client-supplied text and uploads as untrusted input to agents (prompt-injection risk); agents cannot run commands outside the project directory, and destructive commands require owner approval.
- **No GitHub webhook:** Accept happens only in the console, so there is no webhook endpoint or webhook credential (D-279). `accept_gate` and `advance_stage()` are callable only from an owner session, and approvals store the SHA-256 of the approved content (D-264, D-265).
- **Backups:** the database is exported on a schedule and before each project close, encrypted, saved locally and copied to the owner's own cloud drive. Exports never go into this repo (`.gitignore` excludes them). The encryption key lives in a password manager. Exports are kept 180 days and then deleted (D-222), so deleted client data can remain in backups for up to 180 days. One restore of an export into a scratch database is proved in Phase 1; there is no regular restore drill (D-294).
- **Repo hygiene:** the repo is public. GitHub secret scanning and push protection are on; CI (lint, typecheck, unit tests, the database checks and a docs lint) starts in Phase 1, a scripted mutation check runs on every change to `supabase/**`, and branch protection comes later (D-287, D-288). Secret scanning and push protection are on and the old personal access token is revoked (D-292).
- **Uploads:** allowed types are PNG, JPEG, WebP, SVG, PDF, DOCX, plain text, markdown, JSON and MP4, up to 25 MB each, with no zip files. Each upload is scanned for malware in the worker before any agent sees it, SVG is sanitized, agents never open documents with macros, and MP4 is treated as an asset only. The scanner is installed on the owner's machine.
- **Owner notes:** stored in an owner-only table, because clients can read their own project row. The Requirements agent must not quote them in anything the client sees.
- **Run logs:** stored as database rows, may contain client data, and are deleted 90 days after project close.
- **Builder commands:** shell commands run from an allowlist with installs using a frozen lockfile and running install scripts for all packages, only inside the run's container (a package outside the plan and the curated allowlist needs the owner's approval, and the round summary shows the lockfile diff, D-286); deleting a directory or many files, and force-pushing or rewriting git history, pause the run for the owner's answer; everything else (including other network requests) is refused and logged. A waiting run keeps its slot for up to 1 hour and is then parked.
- **Previews:** Vercel previews stay behind Vercel's login and only the owner views them. Screenshots and QC measurements come from a local build the worker serves. No share links, no preview gate.
- **Reader step:** a tool-less step turns client text, uploads and reference screenshots into schema-validated fields, so the Builder never sees raw client content; prompt-injection cases are part of the eval fixtures (D-267).
- **Notes file:** `.pipeline/NOTES.md` in the client repo may not contain the owner's private notes; the owner reviews its diff at each round gate. The clean-history handover leaves it behind.
- **Worker secrets:** the Anthropic key, Supabase service key, GitHub App key and Gmail app password live in a gitignored `.env` file in the worker's folder and rely on full-disk encryption of the owner's laptop (accepted risk: plain text on disk). One Anthropic key serves all projects with no hard spend limit in the Anthropic console (accepted risk); every run has a wall-clock cap and a turn limit and spend gets alerts only (D-276).
- **Reference-site tool:** opens only the client's listed URLs, public web addresses only (no localhost, private network ranges or cloud metadata addresses), with a short timeout; the agent receives screenshots, never page text; screenshots are stored privately and deleted with the project's other data.
- **Form spam and abuse:** every form has a honeypot, a time check and a best-effort in-memory rate limit; an automatic reply is only added when the PRD asks, because an auto-reply to any address can be abused to send mail to third parties.
- **Invites:** client invite links are valid for as long as Supabase allows for its own links, and the console resends them; Supabase's invite and reset emails use the same Gmail through Supabase's custom SMTP.
- **Client write limits:** the database accepts client writes only while a project is `active` and only in the stage each write belongs to (D-216, D-217); after close a client reads only the handover guide. Approvals are append-only, so these limits stop a stray approval from becoming permanent.
- **Email log:** `email_log` records every email with a unique dedupe key, is owner-only, and holds recipient addresses, so the retention job deletes a project's rows with its other data.
- **Supabase MCP server:** `.mcp.json` points at the local Supabase stack and is read-only (D-274). Agents use it for reads and documentation only; any write through it (data, schema, functions, storage, branches, migrations) needs the owner's approval first, and schema changes follow the migration rules in 15-operations.md.
