# Data model (Supabase)

> Originally taken from a Claude Doc (2026-10-05) that has since been retired. The repo is the source of truth; this file reflects the owner-approved decisions recorded in `DECISIONS.md`. Agents change files in `docs/spec/` only after the owner approves a proposal in `docs/proposals/` (see `AGENTS.md`).

The core is a project row with a stage, plus append-only versioned artifacts and approval records. Row-level security limits clients to their own project's client-facing data. The draft SQL, including row-level security policies, is in `supabase/migrations/`.

| Table | Purpose | Key fields |
| --- | --- | --- |
| projects | One per client site; a client reads its own row, so it holds nothing owner-only | id, name, industry, intake_template_id, intake_template_snapshot, stage, status (active, paused, closed), close_reason (completed or cancelled), changes_frozen_at (set by the transfer script; clients cannot submit change requests after it), created_at |
| project_internal | Owner-only fields of a project, one row per project, created with it | project_id, github_repo, vercel_project_id, token_budget, round_plan, retention_days (default 90), retention_until, data_deleted_at (these three come at go-live, G17), cancel_reason (required when a project is cancelled) |
| clients | **Go-live only (D-298, G15; not in the dev-only baseline):** client accounts (Supabase Auth users) | id, email, project_id, is_signer (one signer per project; only the owner sets it) |
| owners | Owner accounts (Supabase Auth users); membership decides the owner role | id, created_at |
| intake_templates | Versioned industry templates | id, industry, version, sections, status |
| intake_rounds | Intake rounds and their lock state | project_id, round, status (open, submitted, reviewed), submitted_at, reviewed_at |
| intake_responses | Answers by round, and the text of every follow-up question; the owner's edits overwrite; the owner can add questions and remove follow-ups; a client can change only the answer, not the round, question or origin | project_id, round, question_id, answer, asked_by (template, agent or owner), question (text of a follow-up; empty for a template question) |
| uploads | Client assets | project_id, kind, storage_path, optional, mime_type, size_bytes (25 MB maximum; images 5 MB maximum), scan_status (pending, clean, infected) |
| artifacts | Versioned agent outputs. `type` is an enum: `intake_record`, `prd`, `plan`, `skill_set`, `round_scope`, `prototype`, `round_preview`, `round_summary`, `backlog`, `qc_results`, `report`, `deployment_checklist`, `handover_guide`, `release_note`; a new type is added by a migration with the task that needs it. Notes on some types: `intake_record`, `prd`, `plan`, `prototype`, `round_summary` (one per build round, carrying the round number in its content), `report`, `deployment_checklist`, `handover_guide` (client-visible; holds the documentation, the handover document and the how-to-ask-for-changes note; the only artifact a client can read after close) and `release_note` (one per change-request mini-round; the owner's deploy approval attaches to it) | project_id, type, version, content, status (draft, approved, rejected, superseded), client_visible (go-live, G15), change_request_id (the accepted change request that allows a new version after the stage has advanced, D-238); a version's content never changes after it is written (a new version is a new row) |
| approvals | Immutable approval log; written only by `accept_gate` (no API role inserts into it); one row per giver, gate and artifact; `at`, `content_sha256` (the SHA-256 of the artifact's content) and `approved_by_email` (a snapshot of the giver's email) are set by the database; `approved_by` is the giver's user id kept as plain data with no foreign key, so the row and the snapshot stay if the login is deleted; such a row stops counting because its giver is no longer in `owners` (D-309) | artifact_id, approved_by, approved_by_email, role (owner or client), gate_type (soft, hard, client), content_sha256, at |
| rounds | Build rounds | project_id, number, scope, preview_url, branch, pr_number, pr_url, claims, claims_cleared_at, change_request_id, status (planned, building, in_review, approved) |
| backlog_items | Questions and assumptions from building | project_id, round, question, context, assumption, owner_answer, ask_client, client_answer, answer_action (next_round or immediate_fix), status (open, answered, assumption_accepted) |
| comments | Client notes on the prototype and on the final screenshots | project_id, body, kind (prototype, final_screenshots), artifact_id, owner_disposition (forwarded, change request, ignored) |
| change_requests | Post-lock scope changes | project_id, description, impact_note, decision (accept_current_round, accept_mini_round, defer, decline), status (received, accepted, deferred, declined, deployed), submitted_by (owner or client), created_by |
| qc_runs | QC results | project_id, lighthouse scores, checklist results, run_at |
| skills_registry | Library index and per-project skills | name, path, scope (project, candidate, library, deprecated), project_id, version, generalization_report (JSONB), approved_by, approved_at |
| stage_runs | Durable queue and run log for the stage runner | project_id, stage, status (queued, running, waiting, cancel_requested, succeeded, failed, cancelled, stopped; `parked` and `parked_at` come at go-live, G16), queued_at, claimed_by, heartbeat_at, attempts (at most 2), tokens_used, trace_id, model, prompt_hash, started_at, finished_at; every status change goes through the claim and transition function and a partial unique index allows one running or waiting run per project |
| gate_config | Gate settings per stage; global rows cannot be deleted and only `escalate_after_hours` changes; a project row cannot change a global gate's gatekeeper | stage, project_id (empty = global default), gate_type, gatekeeper, escalate_after_hours, feedback_cap |
| skill_uses | Optional good or bad marks on skill use | project_id, stage, skill, mark (good or bad), marked_at |
| run_logs | Text log lines for each run, including the step journal; deleted 90 days after project close | run_id, trace_id, level, message, created_at |
| owner_notes | Private owner notes that agents read; owner-only | project_id, body, updated_at |
| email_log | Every email the worker sends or tries to send; the unique dedupe key is claimed before sending; owner-only | project_id (null for owner alerts), recipient_role, recipient, event, dedupe_key, claimed_at, sent_at, error |
| prd_feedback | A client's Request changes note on a PRD version; goes to the owner | project_id, artifact_id, body, created_by, created_at |
| gate_feedback | The owner's Feedback on a draft waiting at a gate; one row per loop (the loop count); append-only, written only by feedback_gate(); the agent reads it | project_id, artifact_id, round, body, created_by, created_at |
| worker_commands | **Go-live only (D-301, G16; not in the dev-only baseline):** console commands for the worker (kind: retry, cancel, resume, end_run, run_retention); owner-only; one open command per kind and target; the worker claims with `FOR UPDATE SKIP LOCKED` | kind, project_id, run_id, requested_by, requested_at, claimed_by, claimed_at, finished_at, error |
| run_approvals | A run's request to the owner before a risky command (deleting files, rewriting history); owner-only | run_id, kind, command, status (pending, approved, denied), requested_at, decided_at, decided_by |

**Stages (project.stage):** intake, requirements, plan, prototype, build_rounds (one repeating stage; the round number is in rounds.number), qc_report, deploy_prep, handover, closed. A stage moves forward only when its artifact has an approval record from an owner or, at a client gate, from the project's named client signer. Paused is a project status, not a stage.

**Also in the model (D-235 to D-239, D-252 to D-256):** `close_project()` is the one routine that closes a project; it sets the status, the reason and `project_internal.retention_until` (closed now plus `retention_days`), and a completed close is refused while an accepted change request is undeployed. The cancel function calls it. `erase_project_data()` is the database step of the retention job: it deletes uploads rows, intake rounds and answers, run logs and `email_log` rows, blanks the handover guide's content and sets `data_deleted_at`, and keeps approvals, the other artifacts and the project row. The named client signer is `clients.is_signer` and the change-request freeze is `projects.changes_frozen_at`. The `stopped` run status is for runs the no-progress watchdog stops; a `parked` run (D-257) has given up its slot after waiting too long, keeps its working folder and branch, and is resumed as a new run. `accept_gate`, the remaining-gates function, the rule that blocks new versions after a stage advances and the cancel function come in their own migrations (D-258 to D-262). A `handover_guide` can be made client-visible only after the owner's hard-gate approval of that version (D-251). Gate rules live in database functions (see 15-operations.md). Security-definer helpers used by policies and gate functions live in a `private` schema that the API does not expose, every security-definer function sets an empty `search_path` and uses qualified names, and execute is granted only to the roles that need it (D-271).

**Dev-only baseline (D-297 to D-304); where this paragraph and the one above differ, this one wins until go-live:** there is no `clients` table, `is_signer`, `client_visible` or client row-level security, no `parked` status or `parked_at`, no `worker_commands` table, no `project_internal.retention_until`, no `erase_project_data()` and no retention job. `close_project()` sets the status and reason and keeps the refusal of a completed close while an accepted change request is undeployed. `cancel_project()` marks queued runs `cancelled` and running runs `cancel_requested`, and the worker aborts them. A `client` approval keeps role `client`; its giver must be an owner, and a CHECK requires a non-empty `approvals.evidence_note` (a free-text note naming the channel). A run is claimed by one database function (`FOR UPDATE SKIP LOCKED`) that skips projects with a running, waiting or `cancel_requested` run and marks a stale `cancel_requested` run `cancelled` (D-302, D-305).
